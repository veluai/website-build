# Repository operating procedure

## Purpose

This file is the naming and change procedure for `veluai/website-build`.
The public site is published in GoHighLevel. A commit or merge in this
repository does not update velu.us. Use
[10.30-publish-to-highlevel.md](10.30-publish-to-highlevel.md) when a change
also has to be published.

[README.md](../README.md) is the human map. [AGENTS.md](../AGENTS.md) is the
agent guide. This file is the procedure both of them point to.

## Folders

| Folder | Use it for |

Also leave these at the root, unnumbered, because tools expect them there:
`README.md`, `AGENTS.md`, `.gitignore`, and `.github/`.

Do not add a README except the repository root and `80-backlinks/README.md`.
`scripts/check-repository.py` allows only those two. The backlinks README is
that folder's index. Every other file there uses an `80.` number.

## Numbering

- Folder numbers go by tens: `10-`, `20-`, `30-`, and so on.
- A file name is the folder number, a dot, a sequence, a hyphen, and a
  readable kebab-case slug: `10.20-changelog.md`.
- Prefer steps of `.10`: `10.10`, `10.20`, `10.30`.
- When `.10` steps are not enough, use `.01`: `40.10`, `40.11`, `40.12`.
  Nine `.10` steps fit in one folder (`20.10` through `20.90`). A tenth file
  needs `.01` steps.
- One topic per file.
- Paired files may share a number and differ by extension, as
  `60-source/60.30-Reviews.md` and `60-source/60.30-Reviews.docx` do.
- Do not create a `Foo 2.md` beside `Foo.md`. The repository check flags that
  pattern. Compare the two and keep one file.
- Image binaries under `50-images/` keep their existing filenames. Only the
  inventory markdown at the folder root is numbered (`50.10-image-library-inventory.md`).

## Where new work goes

- A change to a live page is edited in that page's `40-pages/` files.
- A new standard goes in `20-standards/`.
- A published implementation record goes in `30-current-site/`.
- A backlink audit, snapshot, inventory, or gap note goes in `80-backlinks/`
  at the next free number in `80.10`–`80.49`. A recommendation or log entry
  goes in `80.60`–`80.89`. Link
  [30.45](../30-current-site/30.45-backlink-preservation-audit-2026-06-29.md)
  instead of copying it. Implement one recommendation ID at a time.
- Work that is not live yet goes in `70-implementation/`. The November 15 appointment page sources are live-verified in `40.93`–`40.98`;
  their outstanding runtime/marketing follow-up stays in `70.30`. Get Started
  remains the live Discovery booking page.
- When an unpublished page becomes live, `git mv` its sources into `40-pages/`
  as a new block, update
  [30.10-current-site-index.md](../30-current-site/30.10-current-site-index.md),
  and add a changelog entry. Do not leave live copy in `70-implementation/`.

## Nesting

Keep files flat inside each numbered folder. Three nests are intentional:

1. `50-images/<page>/` holds that page's image files. Flattening the binaries
   into one folder would be harder to browse. Page slugs in use: `about`,
   `client-advisory`, `get-started`, `grant-advisory-compliance`, `home`,
   `outsourced-accounting`, and `tax-services`.
2. `30-current-site/evidence/<dated-pack>/` holds dated proof packs
   (screenshots and JSON). Packs in the repository today:
   `business-identity-2026-10-28` and `google-follow-up-2026-10-28`.
   Local-only screenshots stay ignored under
   `30-current-site/evidence/local-verification/`.
3. `.github/workflows/` is required by GitHub. It is not a content folder.

Case studies and the Search Console extract are flat files in `60-source/`.
Do not put them back into subfolders.

## Making a change

1. Branch from current `main`. Confirm the working tree before editing.
2. Edit the numbered file for that topic. For a rename or a move, use
   `git mv` so history follows the file. Update every reference in the same
   change: validators, `60-source/60.20-image-layout-reservations.json` when
   CSS paths change, `AGENTS.md`, and Markdown links.
3. Run the checks in [AGENTS.md](../AGENTS.md) and
   [10.30-publish-to-highlevel.md](10.30-publish-to-highlevel.md).
4. Open a pull request with `.github/pull_request_template.md`. State whether
   HighLevel publication is not applicable, prepared, saved, published, or
   live-verified.
5. After merge, publish in GoHighLevel only when the task includes
   publication. Record the result in the changelog and in the relevant
   implementation file. Keep prepared, saved, published, and live-verified
   distinct.

Do not add an application build, a deploy pipeline, or a second copy of a
canonical file. Do not invent services, prices, reviews, credentials, offices,
hours, or geographic coverage.
