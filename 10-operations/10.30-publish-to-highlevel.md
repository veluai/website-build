# Publish to GoHighLevel

This is the sequence for moving a repository change onto velu.us. Merging a
pull request does not publish the site. Local validators do not prove that a
page is live or that JSON-LD is valid in Google's eyes.

Use the status words exactly, and do not skip ahead:

| Status | Meaning |
| --- | --- |
| Not applicable | Repository-only change. Nothing is published in GoHighLevel. |
| Prepared | Source is ready in this repository and is not yet saved in GoHighLevel. |
| Saved | Saved in GoHighLevel and not published. |
| Published | Published in GoHighLevel. Live checks are still open. |
| Live-verified | Published, and the checks below were done on the live URLs. |

## 1. Prepare in the repository

- Work on a focused branch from current `main`.
- Edit the numbered source files. Use `git mv` for renames.
- Follow [10.10-repo-operating-procedure.md](10.10-repo-operating-procedure.md)
  for where the file belongs. Unpublished pages stay in `70-implementation/`
  until they are live.
- Keep page copy, JSON-LD, and HTML changes limited to what the task
  authorizes. Identity, footer, and email rules are in
  [AGENTS.md](../AGENTS.md).

## 2. Validate before the pull request

Run these from the repository root:

```text
python3 scripts/check-repository.py
python3 scripts/validate-business-identity.py
python3 scripts/validate-image-layout.py
python3 -m unittest discover -s scripts -p 'test_*.py'
git diff --check
```

`check-repository.py` checks one root `AGENTS.md`, no README outside the
repository root, no numbered duplicate filenames, and local Markdown file
links. It does not check external URLs or heading anchors.

Review the diff for unrelated edits.

## 3. Open the pull request

Use `.github/pull_request_template.md`. Record the HighLevel status, the
pages involved, and any remaining work. Link the implementation record when
there is one.

## 4. Merge does not publish

After merge, the canonical checkout needs a pull. The live site is unchanged
until someone publishes in GoHighLevel.

## 5. Publish in GoHighLevel

When the task includes publication:

- Preview the affected pages on desktop and mobile, including the shared
  footer when footer source changed.
- Append image-reservation CSS through native Custom CSS. The blocks live in
  `40-pages/40.xx-*.css` and are mapped from
  `60-source/60.20-image-layout-reservations.json`. Do not inject that CSS
  through late tracking code.
- Keep Cloudflare `<!--email_off-->` comments around public contact email
  markup. Do not replace those with JavaScript email links, and do not change
  global Cloudflare settings from this workflow.
- Save, then publish, only the pages in scope.

## 6. Live-verify

After publication, check the live URLs listed in
[30.20-business-identity-implementation.md](../30-current-site/30.20-business-identity-implementation.md)
when the change is sitewide, or the specific page URLs when it is not.
Check phone and email links, legal links, and the rendered JSON-LD.

For email changes, compare the delivered HTML with the rendered page. A
browser can show a normal email address while the response still contains
`/cdn-cgi/l/email-protection`.

## 7. Record the result

Update the implementation record and
[10.20-changelog.md](10.20-changelog.md) with the date, the files changed,
the evidence, outstanding checks, and rollback steps. Set the status to
prepared, saved, published, or live-verified. Do not mark live-verified
from repository source alone.

Move a page from `70-implementation/` into `40-pages/` only after that
live verification, and update
[30.10-current-site-index.md](../30-current-site/30.10-current-site-index.md)
in the same change.
